YouTube 客户端现状与 PO Token 问题跟踪记录
=============================================

记录日期：2026-08-05
用途：下次继续研究 YouTube 4K 下载时，快速恢复背景和测试结论。

一、背景与当前方案
------------------

- 用户长期使用公共 VPN 机房 IP。匿名访问是否可用与出口 IP 明显相关；被拦截时使用“斗地主模式”通过 Firefox Cookies 保底下载。
- 当前最可靠的是“斗地主模式”：web_safari + Firefox Cookies + HLS，最高约1080P。当前实测中，不同视频、不同 VPN IP 均能下载。
- 4K 需要独立 DASH 视频流和音频流。目前重点研究 mweb + PO Token Provider；是否传入 Cookies 必须分开记录。
- android_vr、visionos 不支持账号 Cookies，成功与否依赖出口 IP，不适合当前使用环境。
- PO Token、bgutil 和 Deno 组件继续保留，等待后续适配。

测试环境：Windows 10；yt-dlp Nightly 2026.08.04.234419；bgutil 1.3.1；BgUtils 3.2.0；Deno 2.5.6；GCP 与 Linode 美国出口 IP；部分路线使用 Firefox Cookies。

当前软件配置：

- 普通下载：mweb + bgutil PO Token + Deno，不传 Firefox Cookies。
- 斗地主模式：web_safari + Firefox Cookies + HLS，不启用 PO Token Provider。
- 播放列表模式：mweb + bgutil PO Token + Deno，不传 Firefox Cookies；逐条下载并保留原有续传、跳过和失败后继续逻辑。

二、关键实测结果
----------------

1. web_creator

当时成功样本：https://www.youtube.com/watch?v=CpGiJ3VRjps

- 能生成 Token；480P 独立音视频流完整下载并由 FFmpeg 合并。
- 能列出3840×2160格式；没有下载完整4K文件。

当时失败样本：https://www.youtube.com/watch?v=ap8Hw5U74nY

- 使用与成功样本相同的 Cookies、组件和公网 IP。
- 在 BotGuard / integrity token 生成阶段失败，尚未进入格式选择和下载。
- 底层错误：BGError: VM operation timed out（code: TIMEOUT）。

同日跨 IP 对照：

- 成功视频：https://www.youtube.com/watch?v=2FBRvGz94a8
- GCP 与 Linode 美国 IP 下都能生成 GVS PO Token，并取得最高3840×2160格式；480P独立视频流和音频流均完整下载并合并。
- Linode 首次下载曾因 Googlevideo CDN 域名 DNS 解析失败而终止，重新提取后换到其他 CDN 域名即完整成功；该次失败不属于 Token 失败。
- 失败视频：https://www.youtube.com/watch?v=u41y8KC9L5k
- GCP 与 Linode 美国 IP 下均超过124秒仍未完成 Token/格式获取，最终由测试超时终止；没有取得可下载格式。

结论：web_creator 存在稳定的视频差异；同一成功视频在两个 IP 下都成功，同一失败视频在两个 IP 下都失败。当前对照中，切换 GCP/Linode IP 没有改变这两个视频的 Token/格式获取结果。

2. mweb

- 带 Firefox Cookies：对原有对照样本都能生成 Token、取得4K格式并开始下载，但每次完整下载都会在约5%左右返回 HTTP 403。
- 不带 Firefox Cookies，测试视频：https://www.youtube.com/watch?v=2FBRvGz94a8
- GCP IP：成功生成 GVS PO Token，取得最高3840×2160格式；480P独立视频流和音频流完整下载并由 FFmpeg 合并，全程无403。
- Linode 美国 IP：稳定返回 LOGIN_REQUIRED（Sign in to confirm you’re not a bot），尚未进入格式获取和下载；用户通过切换这两个 IP 可重复复现差异。
- 上述无 Cookies 对照只改变出口 IP，视频、mweb、yt-dlp、bgutil、Deno 和命令参数保持一致。

结论：mweb 不带 Cookies 时呈现明确、可重复的出口 IP 差异；GCP IP 可完整下载，Linode 美国 IP 会触发机器人验证。mweb 带 Cookies 的约5% HTTP 403是另一组独立现象。

3. web_safari / 斗地主模式

- 必须传入 Firefox Cookies；不传 Cookies 不属于该模式的正确用法。
- 当前实测可在公共 VPN IP 下稳定下载最高约1080P的HLS流。
- 不依赖 GVS PO Token，是可靠的1080P保底方案，不是4K方案。
- 下载字幕时同时请求作者字幕和自动字幕；部分字幕仍可能受到字幕 PO Token 限制。

4. android_vr / visionos

- 不支持账号 Cookies，传入登录 Cookies 时 yt-dlp 会跳过客户端。
- 干净 IP 下曾成功取得4K并完整下载480P测试文件。
- 公共 VPN IP 下会出现机器人验证或无法取得指定 DASH 格式。

结论：只适合干净 IP 下实验，不适合作为当前稳定主方案。

三、已排除的方向
----------------

- 不是画质表达式或 FFmpeg 故障：成功样本已完整下载并合并480P独立音视频流。
- 不是没有读取 Cookies：日志已识别 Firefox 登录 Cookies。
- Firefox 能正常播放，不代表 BgUtils 能完成同一视频的 BotGuard 挑战。
- 更新到当时最新 Nightly、延长 BotGuard VM 等待时间或更换公网 IP，均未稳定解决。
- BgUtils 4.x 有破坏性 API 变化；隔离做过最小适配，仍未得到正常 integrity token，不能直接替换3.2.0。

四、官方线索
------------

- 官方 PO Token Guide 推荐 mweb + PO Token Provider。
- mweb、web_creator、web_safari 支持账号 Cookies；web_creator 明确要求登录。
- android、android_vr、ios、visionos、tv_simply 不支持账号 Cookies。
- PO Token 可能绑定客户端、账号/访客会话或视频ID，不同客户端的 Token 不能混用。
- 已有“mweb取得Token后403”和“生成的Token不被GVS接受”的相似报告；尚未找到 BGError: VM operation timed out 的明确官方结论。

相似 Issues：

- mweb Token 后403：https://github.com/yt-dlp/yt-dlp/issues/14421
- web_creator 视频ID绑定：https://github.com/yt-dlp/yt-dlp/issues/16144
- Token生成后GVS仍403：https://github.com/yt-dlp/yt-dlp/issues/15789
- android_vr 最新变化：https://github.com/yt-dlp/yt-dlp/issues/17348

------------
