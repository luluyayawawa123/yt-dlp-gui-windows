YouTube 下载技术与问题研究记录
最近更新：2026-11-11

文档用途

本文件用于技术交接。以后 YouTube、yt-dlp 或 PO Token 组件发生变化时，技术人员或 AI 应先阅读本文件，再结合当次完整日志和官方最新资料继续研究。本文记录的是当前软件实际采用的方案、历史问题、已验证结论和后续研究入口；当前事实最终以代码和实际日志为准。

一、当前下载方案

普通下载：mweb + Firefox Cookies + bgutil PO Token。
完整链条：Firefox 登录信息 → yt-dlp 的 mweb 客户端 → bgutil Provider 插件 → Deno 运行 generate_once.ts → bgutils-js/BotGuard 生成 PO Token → yt-dlp 获取视频与音频地址 → FFmpeg 合并。

普通下载开始新任务或手动点击“下载重试”时，都会清除该视频的旧 Token 缓存并预热 Deno/bgutil，从第 1 轮第 1 次重新开始；已有文件保留供断点续传。2026-11-11 普通模式新增媒体 403 恢复（v1.1.10）：最多 3 轮，每轮 3 次（含首次），每次重新解析地址并尝试断点续传；本轮耗尽且仍为媒体 403 时，仅清理当前视频缓存，下一轮重新请求 Token，最多自动清理 2 次。任务卡片只在重试过程中显示轮次、次数，恢复下载后正常显示进度、速度和剩余时间；取消即停止，缓存清理失败不继续换轮。DNS 等其他错误、字幕补救及播放列表规则不变。本轮改动通过 52 项回归测试，已在一次真实 403 故障中恢复续传，详见后文；v1.1.10 绿色版待用户打包验证。

播放列表/频道：mweb + Firefox Cookies + bgutil PO Token。软件先读取列表，再逐条下载；每个新视频都会清除一次自己的旧 Token 缓存。媒体 403、DNS 解析失败、PO Token 启动超时或生成失败会触发重新解析和断点续传，首次加自动恢复最多尝试 6 次；同一视频自动恢复时保留现有 Token。登录验证或 Cookies 不可用会停止整个列表，其他视频最终失败后记录原因并继续下一个。

播放列表支持按语言选择作者字幕，并分别统计视频和字幕结果。正常下载模式下，字幕失败后会刷新 Token，再进行一次仅字幕补救；“仅下载字幕，不下载视频”模式最多尝试 6 次，从第 2 次开始每次刷新当前视频的 PO Token。该选项只属于播放列表，不影响普通下载模式。视频加字幕和仅下载字幕均已通过 13 条播放列表的开发版实测。

普通下载中的“斗地主模式”：web_safari + Firefox Cookies + HLS，不使用 PO Token，最高尝试下载 1080P；勾选字幕时也会尝试自动字幕。它只是高画质方案失效时的临时兜底。

二、历史问题与解决结果

旧版曾出现两类主要问题：

1. BotGuard VM operation timed out
旧版 web_creator + Firefox Cookies 在生成 PO Token 时出现过 VM 超时。该问题不能与媒体下载阶段的 HTTP 403 混为一谈。

2. 已生成 PO Token，但下载媒体时返回 HTTP 403
bgutil Issue #242 最终定位到 BotGuard challenge 与同一次 YouTube 首页会话中的 ytcfg/EVENT_ID 没有正确对应。BgUtils #44 和 bgutil PR #243 修复了相关逻辑，随后官方发布 bgutil 2.0.0。本项目曾提前应用该修复验证，之后已改用官方 2.0.0 整套组件，不再保留本地补丁。

3. MWeb 只返回 SABR 流，常规格式不可用
2026-11-02，本项目 Issue #8 的 v1.1.7 日志确认：Firefox Cookies、GVS PO Token 和字幕 PO Token 均获取成功，但 YouTube 对该账号的 mweb 响应只提供 SABR 流，常规 HTTPS 视频、音频格式缺少下载 URL，最终报“Requested format is not available”。这不是 PO Token 生成失败，也不是普通的媒体 HTTP 403。

yt-dlp 官方说明，YouTube 正在对不同账号、会话进行 SABR-only 灰度和 A/B 测试，因此相同视频在不同用户、账号或时间下可能出现不同结果，本地未必能够复现。正式版和 Nightly 目前尚未包含完整的 SABR 下载器。

官方 SABR 下载器 PR #13515 已提供前沿测试版，但截至 2026-11-05 仍未合并，存在代码冲突、部分测试失败及其他未完成问题。

2026-11-05 本地实验：在 bin 中复制旧内核后，直接替换为维护者 2026-10-27 发布的 SABR 构建，已核验附件 SHA256。客户端、Firefox Cookies、Provider 和软件代码均未改变。
V5D7ZBeNEUw 实测：原参数通过 HTTPS 完整下载 480P 音视频及英语作者字幕，合并 MP4、转换 SRT 成功；强制 protocol=sabr 后，同样完整下载并合并成功，日志明确显示 Invoking sabr downloader。仅字幕下载成功；斗地主 HLS 小片段下载成功。格式清单同时包含 4K HTTPS 和 SABR，未下载完整 4K 视频。44 项本地回归测试通过。
Issue #8 样本 bDcpG7rThMw 已能列出 SABR 音视频格式，本次清单最高为 1080P；尚未验证报告者原账号环境。播放列表整批下载和绿色版仍需后续实测，不能据此宣称全部场景已解决。
2026-11-05 SABR 断点续传实测通过：强制 SABR 480P，在约 15% 时终止测试进程树，再用相同参数和输出文件名重启。日志明确显示音频 140-0、视频 397-0 均 Resuming download，随后完整下载、合并成功；成品经 FFmpeg 全文件解码无错误，SHA256 与此前不中断的 SABR 下载成品完全一致。本次验证的是命令行真实中断续传，不等于已测试 GUI 按钮的全部交互场景。
2026-11-05 用户普通模式实测 u05nNwhysEM：使用新内核、原 MWeb/Cookies 参数，通过 HTTPS 下载 4K 视频和英语作者字幕，用户确认最终任务完成；提供的阶段日志没有 403 或重试。该结果证明原链路兼容，不等于已验证报告者的 SABR-only 账号故障。
测试文件和日志已清理，未提交或公开。使用 bin/更新SABR内核.bat 保持实验渠道，切回 Stable/Nightly 会失去本实验构建的 SABR 支持。

三、常见故障必须分开判断

LOGIN_REQUIRED / “Sign in to confirm you’re not a bot”
这是 YouTube 要求登录验证，通常发生在生成 PO Token 之前，不等于 Token 生成失败。普通下载和播放列表都应先确认 Firefox 已登录 YouTube。历史实测中，不带 Cookies 的 mweb 在 GCP 出口 IP 下可以下载，在 Linode 美国出口 IP 下稳定失败；其他测试也收到过 LOGIN_REQUIRED，因此播放列表后来改为与普通下载一样传入 Firefox Cookies。出口 IP 仍可能影响下载，但不能据此认定 IP 是唯一原因。

PO Token 生成失败
应查看 bgutil/BotGuard 给出的底层错误，例如 TIMEOUT、脚本不可用或组件版本不匹配。只升级 yt-dlp 不一定能解决 Provider 自身的问题。

媒体 HTTP 403
指已经取得格式和下载地址，但 googlevideo 媒体请求被拒绝。软件会重新解析地址并尝试断点续传，但重试不保证成功。新版再次出现 403 时，应保存完整日志，不能直接认定为旧版 Issue #242 复发。

2026-11-11 仍未解决：获取 Token 成功，但媒体 HTTPS 请求反复 403
当前链路为 MWeb + Firefox Cookies + bgutil 2.0.0 / BgUtils 4.0.3 + SABR 实验内核 2026.10.27.135913。软件没有强制 SABR，以下失败任务实际使用 HTTPS；网页可以播放最高画质，也不保证同一视频能被软件下载。

样本 0uiPISdJA54：美国 Linode 出口未换，4K MP4 请求连续 403，换 Nightly 仍失败；强制 4K SABR 的 --test 短测出现 Token 无效提示，音频为空，未得到有效成品，不能把它的 100% 进度视为成功。480P HTTPS 和 SABR 均完整下载成功。之后 4K 曾恢复，但恢复原因未确定；不再将“更新 Firefox”列为修复方法。

样本 04rfnd1YdyU：最高 1080P，Firefox 可正常播放；软件「最高 MP4」选中 399+140-20，6 次均在视频请求时报 403。「最高画质」选中 399+251-20，也在相同的 399 视频请求时报 403。两个新任务的 Token 不同，各任务内部 6 次重试复用同一 Token、重新解析不同地址，说明不是新任务没有清缓存。

对照验证：清除该视频缓存后，一次命令以最高 MP4 参数成功完整下载 1080P 音视频并合并，实际 Token 与失败任务不同。随后固定使用软件失败日志中的 Token，普通命令和 QProcess 均短测 403；QProcess 换成先前成功的 Token 后短测成功。两次 QProcess 对照保持其他参数一致，出口 IP、媒体服务器及视频格式也相同。再次连续两次清缓存、分别取得不同的新 Token：第一次 403 且零媒体数据，第二次收到音视频数据、无 403。该结果不支持“命令每次都成功”或“清缓存必定解决”。短测成功只确认收到数据，不代表已验证完整视频。

当前结论：故障与所用 Token / 播放会话存在关联，不是 GUI 独有问题；但尚不能判定为某个组件的生成 bug，也未确定 IP、会话等因素的作用。此前 403 自动恢复不刷新 Token，因而可能连续复用同一失败 Token。现已在普通模式实现上述三轮恢复规则，尚未证明能稳定解决；播放列表未改。

2026-11-11 后续观察：用户没有更换出口 IP，先前同一视频多次新建任务、每次重试满仍持续 403；后来测试原视频及多个新视频，均首次尝试就成功，未触发换轮。命令也有成功和失败，不能归为“GUI 不行、命令就行”：一次单独完整下载成功，之后固定 Token 对照有成功有失败；最后连续两次刷新 Token 的短测顺序是先 403、后成功。故障具有明显时变性，不能把暂时恢复认定为 IP 已变好、刷新 Token 必定有效或新重试策略已治愈问题。新机制通过自动化测试、正常下载实测通过，但真实 403 后的三轮切换恢复仍待复现；后续偶遇故障时保存日志验证，无须为凑失败反复下载。

2026-11-11 真实恢复验证：用户随后在同一视频 04rfnd1YdyU、最高 MP4 档位复现 403，截图先显示第 1/3 轮第 3/3 次重试，再显示第 2/3 轮第 1/3 次已清除旧 Token；随后恢复正常下载，进度达到 26.4%，速度和剩余时间正常显示。这证明新机制在本次故障中成功换轮并恢复续传，不等于根因已修复或今后每次都能恢复。记录时尚未收到整段下载及最终合并完成的确认。

DNS 解析失败
属于网络、代理、VPN 或 DNS 问题，与登录验证和 Token 生成是不同故障。

四、以后出现问题时怎么研究

1. 保存从 Command-line config 开始到最终报错为止的完整 verbose 日志。
2. 先判断失败发生在哪一阶段：读取网页、登录验证、生成 Token、解析格式、下载媒体、合并文件。
3. 记录当时的 yt-dlp、Provider、bgutils-js、Deno 版本，以及使用的客户端、Cookies 状态和出口网络。
4. 使用同一个视频做对照测试；不要因为某一次成功或失败就认定方案永久有效。
5. 优先查看官方发布、官方文档和已有 Issues，不凭猜测修改客户端或 Token 逻辑。
6. 更新 Provider 时，server 与插件 ZIP 必须使用同一版本；不要只替换其中一个，也不要随意单独升级 bgutils-js。
7. 修改后至少验证普通下载、字幕、播放列表和重新打包的绿色版。
